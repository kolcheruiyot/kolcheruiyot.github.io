So, I hold my own opinions on why OOP, especially polymorphism is a terrible design.
This might be because of the hours of content I have watched on the matter, or something about
@Primeagen drilling it into my head with his reacts. But, I would like to take a moment, take a step
back and look at it with a birds eye view.
I am in no way shape or form a professional in this matter, but I am C++ developer, and 
I have my opinions on OOP.

To prefix, I do not think OOP itself is bad. In fact, C++ exists because C did not have classes.
And thank god Bjarne decided to implement his own language after Simula failed him. But just
like how name mangling caused this fiasco of having the ability to write functions with the same
name whilst having different arguments, I think Bjarne made C with classes a thing with the kindest 
intentions. As I sit here typing, in 2026, reflections has been introduced to C++26, and even though 
Herb and his team, the WG21, might have the best intentions with the feature, heresy will still be committed
using this new feature.

I take polymorphism and inheritance as this "genie in a bottle" that should always be kept in its lamp.
We have all watched alladin. We all know what genies do, yet, everyone dabbles with inheritance and polymorphism
without a care in the world. 
I personally stand with the opinion that, if you do not know what is happening underneath the hood, then
playing with the fire that is inheritance and polymorphism should not even be in your tools of abilities.
So, underneath the hood, what does that mean?
Assembly. The engine that runs all your code. At the end of the day, your C++ code will end up being lines
of ones and zeros, but since none of us wants to go back to the good old days of punch cards, let us take this 
discussion an abstraction higher, Assembly.
In Assembly, for those of you who have learned that marvellous language, know that there are no classes.

So, your classes will end up being decomposed into something else. In my examples, I will be using AT&T
format Assembly, which, I think is the best form of assembly, but that is a discussion for another blog post.
So, let us look at what a C++ class is underneath the hood.

so a class that looks like this
```C
class CLASS{
public:
    CLASS(unsigned int _value): _VALUE(_value){}
    void call_METHOD(){
            this->_METHOD();
    }
private:
    void _METHOD(){
            _VALUE += 1;
    }
private:
    unsigned int _VALUE;

};

int main(){
    CLASS _class_instance = CLASS(10);
    _class_instance.call_METHOD();
}
```

would become
```asm

        movl    -12(%rbp), %edx
```

cleaning the assembly up a bit, removing memory movements, 

```asm
CLASS::CLASS(unsigned int) [base object constructor]:
        pushq   %rbp
        ; class stuff
        ret
        .set    CLASS::CLASS(unsigned int) [complete object constructor],CLASS::CLASS(unsigned int) [base object constructor]
CLASS::call_METHOD():
        pushq   %rbp
        ; method stuff
        ret
CLASS::_METHOD():
        pushq   %rbp
        ; method stuff
        ret
main:
        pushq   %rbp
        ; move args to %rdi
        call    CLASS::CLASS(unsigned int) [complete object constructor]
        ; move args to %rdi
        call    CLASS::call_METHOD()
        ; clean up to ret 0
        ret
```

notice, that in this case, classes, underneath the hood are functions with "access restrictions".
After moving the right arguments to the right registers, it just becomes function calls. 

continuing with this logic, then, a class inside another class will become a function inside another function.
```C
class A{
    public:
        A(int _value): _VALUE(_value){}
        void call_METHOD(){
            this->_METHOD();
        }
    private:
        void _METHOD(){
            _VALUE += 1;
        }
    private:
        int _VALUE;

};

class B{
    public:
        B(int _value) : a_inst(A(10)) {

        }
        void call_METHOD(){
            this->_METHOD();
        }
    private:
        void _METHOD(){
            a_inst.call_METHOD();
        }
    private:
        A a_inst;
};

int main(){
    B _class_instance = B(10);
    _class_instance.call_METHOD();
}

```
```asm
A::A(int) [base object constructor]:
        pushq   %rbp
        ret
        .set    A::A(int) [complete object constructor],A::A(int) [base object constructor]
A::call_METHOD():
        pushq   %rbp
        ret
A::_METHOD():
        pushq   %rbp
        ret

    ;;;;;
B::B(int) [base object constructor]:
        pushq   %rbp
        call    A::A(int) [complete object constructor]
        ret
        .set    B::B(int) [complete object constructor],B::B(int) [base object constructor]
B::call_METHOD():
        pushq   %rbp
        call    B::_METHOD()
        ret
B::_METHOD():
        pushq   %rbp
        call    A::call_METHOD()
        ret

				;;;;
main:
        pushq   %rbp
        call    B::B(int) [complete object constructor]
        call    B::call_METHOD()
        ret
```
As you can see, no matter how many classes we write, it will still be functions in asm.
which in turn becomes function calls.
the code could end up being long, arduous to read and debug in assembly, but still
performant as classes could be.

this is not the case in inheritance and polymorphism
